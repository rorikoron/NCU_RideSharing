# NCU_RideSharing
辺鄙な場所にある大学なため、弊校ではライドシェアが盛んにおこなわれています。しかし、現行の方式では主にLineのオープンチャットで募集、勧誘が行われており、沢山の問題を抱えています。
そこで、専用のウェブサイトを作成し、これらの問題に対して様々なアプローチを試みました。（最終的には時間や金銭的な面の都合上、8割ほどの完成度でローカルでホストするにとどまりました。）
![image](https://hackmd.io/_uploads/HJ-0-_ghge.png)

## 使い方
`/frontend` にて `npm i` で依存ファイルをインストールしてください。
`run.bat` を起動するとフロントエンドとデータベースが立ち上がります。
フロント側のUIは以下の通りで、ユーザ側は自由に新しく提起、または募集中のライドシェア案に参加でき、ドライバ側は提起されたライドシェア案に対して値段を提案できます。（所謂逆マッチング方式で、オークションの様な方式です。）
![image](https://hackmd.io/_uploads/SJ1ikYgneg.png)


## 技術選定
- Vue Router
- Vue
- Pinia
- Pocketbase（UIありのマネージドDB+Backend）
- Github Actions(Dev Ops)
初級の授業な事もあり、フロントエンドではReactではなく、バニラのHTML/JSを移植しやすいVueを選択。
とにかく時間がなく、私(@rorikoron)がトラブルシューティングなども担う必要あるため、状態管理とDB, Backendにはコミュニティが成熟し、ある程度使いなれているPiniaとPocketbaseを選択。
開発は主に私(@rorikoron)が主導し、GithubでTodoをIssueとして切り分け、チームメンバーが拾っていくという形をとった。
Github ActionsではチームメンバーがIssueに対しプルリク時に自動でReviewerを私アサインし、一々連絡を挟むのをなくした。

## 従来の方法で抱えていた問題点とその対策
- 募集状態が分かりにくい（募集中/満員/中止/マッチ済み）
    - 参加中人数、上限人数を明記することでドライバのキャパを超えなくする。
    - 中止/マッチした場合ドライバと参加者に通知を送り、募集一覧から削除することでユーザを惑わせないよう設計
    - ![image](https://hackmd.io/_uploads/r1CegYl3ex.png)

- 問題のあるユーザが分かりにくい
    - アカウント登録を義務化
    - 双方向のレーティングを導入することで分かるよう設計。DBの構成上受けたレビュー一覧も確認可能。（時間が足りず未実装）
- 出発/到着地点が分かりにくい
    - 募集をかける時に大々的に表示するように。
- ライドシェアの履歴が分かりづらい
    - 一覧を設けることに。（時間が足りず実装できなかったが、動的ルーティングし、他者の履歴も見ることができるようにすることも可能）
    - ![image](https://hackmd.io/_uploads/ryCkxFxnex.png)

- 同じ行先、日時の人が見つけづらい
    - フィルターを設け、容易に検索可能に

## 反省点
- DBはローカルか、臨時でどこかにホストしてもよかったかもしれない
    - データの操作でDBにchangeが追加される。
    - DBの知識を持っているのが私だけだったので前向きに検討しなかったが、それぞれにデバッグ用にデータは必要だった。
- テストを導入するべきだった
    - 初めてReviewerとしてコードレビューを担当したが、仕様と全然違う提出もあったりで、テストを書いた方が速かった気がする。
    - せめて関数単位に切り分けてテストを導入してもいい気がした。
- Github ActionsでCopilotあたりにレビューさせてもよかったかもしれない。
- 能力の異なるメンバーに仕事をアサインする時、個々人の能力を鑑みるべきだった
    - issueを拾わせる形式をとっていたが、APIへの理解があるものとないもの、スキーマへの理解があるものとないものでできる仕事は違ったはずだ。
    - もっと効率の良いアサインの方法はあったはずなので、今回の反省を生かしたい。
